# Feature-completeness gap audit — 9 November 2026

Audited worktree baseline: `01c5d22e104a0f2c89ea42ce1241427f883a0a2d` (package version 0.27.21). Scope: build spec §3, every row and accompanying obligation in §5.1–5.9, all 73 existing ledger IDs, and §12. This is a source/test audit, not an executed Stella comparison or a shipped-desktop qualification. No application code, tests, original ledger, or handoff files were changed. Electron was not launched.

The app is much further along than the original ledger suggests, but it does **not** meet §3 yet. The largest blockers are corpus reconciliation, option/domain conformance, the missing via-snub morph, common workflows hidden by Expert mode, and release qualification. Rebuilding existing generators, faceting, reinforcement, formatted element content, or replay would waste work: those are already mounted implementations. Conversely, registering a source with a classification label does not validate its classification.

## How to read this audit

* **done**: a user-reachable implementation satisfies the named workflow in the stated domain, with identified automated tests. This is implementation completion; it does not mean every option passed in the shipped desktop. **partial**: substantial working behavior exists, but a stated requirement/domain/access/validation obligation remains. **missing**: no implementation of the whole requirement. **out-of-scope-justified**: explicitly excluded by the spec. No whole §5 requirement is dismissed as out of scope; some subfeatures are genuinely missing.
* Proposed ledger **validated** means a done row has directly relevant checks rerun here; **implemented** means a done implementation has inspected test coverage but its complete relevant suites were not rerun here. **partial** and **missing** retain their ordinary meanings. Neither validated nor done is a declaration of executed Stella 6.0 conformance. `baselineAuditComplete` remains false.
* Evidence below names implementation functions/classes and test files. All paths are relative to the repository. Tests listed in a row are coverage evidence; only the explicit execution list near the end was rerun. Static wiring, mounted fake-DOM tests, native subprocess tests, scripted Electron scenarios, old artifact reports, and actual shipped-app execution are different evidence levels. Existing smoke scripts are reproducible scenarios, not evidence that they passed today.
* UI paths describe the final mounted layout, after `organizeInspector`, `ConstructGallery`, `NetsFlow`, `AppChrome`, and `AppearanceSheet` move existing elements. Open **Inspector** (`toggle-inspector`) first. **A** = Analysis, **C** = Construct, **N** = Nets, **X** = Advanced. A Construct tool card has ID `construct-card-<tool-id>` and opens the existing tool's controls. A collapsed disclosure is accessible; an ancestor with `data-expert` is not accessible without enabling Expert tools. Construct Expert cards are a distinct case: their panes do not inherit the card's `data-expert`, so Ctrl+K can reveal those controls without switching Expert mode. The table calls this a hidden-card discoverability gap, not absent computation or strict access gating.
* New-user column: **yes** = no Expert mode needed; **mixed** = a required/common portion is gated; **expert** = only Expert access. The sentence after the semicolon is the recommended policy. Command-search revealing an expert control can automatically enable Expert mode (`app-chrome-reveal`); that does not count as access without Expert mode. Hidden-mode smokes deliberately enable experts and cannot establish novice accessibility.
* Remaining effort: **S** ≤2 h, **M** 2–6 h, **L** multiple worker packages. Estimates include targeted tests/documentation, not specialist review, access to absent corpus sources, hardware procurement, or undocumented baseline discovery. Dependencies cite requirement IDs and the work packages below. A dash in the gap column means no additional implementation gap identified within the stated workflow; the global §3 release gates still apply.

## Prioritized worker backlog

Each named package is one worker's **2–6 h slice**, with an observable exit condition. L requirements need several such slices. Rounds are dependency waves, not a claim that three rounds can discover and validate an absent 2,191-model corpus. In particular, R7-CORPUS-SHARD is a repeatable queue of independently assigned 2–6 h packages, with the shard size set after timing the first shard. If source data or baseline semantics remain unavailable, the honest result is a blocked named gap and a partial release, not a feature-complete declaration. No research extension is on the critical path.
